Technical

Architecture

Swift owns the pixels. Rust owns the bytes. This page shows how the two halves split the work, how an outside change reaches your screen, and which decision records chose each piece.

The split

The Mac app is Swift 6 and AppKit. It owns every pixel and the keystroke path: the text view and its layout, drawing, the system text services (spell check, Writing Tools, dictation, the find bar), documents, windows and menus.

The engine is Rust. It owns the bytes: decoding, parsing, the change engine, snapshots, the path jail, diagram and math rendering, collaboration, export, and the dewline command with its MCP server. One engine serves the app, the Quick Look preview and the command.

On the keystroke path the engine does one thing. It parses the edited window, at most 4 KB, with no locks held and no I/O (0006).

Two other designs were ruled out. A pure Rust UI has no VoiceOver for text, no Writing Tools, no find bar, no Services and no spell check, and rebuilding them was estimated at 28 weeks of solo work. A web view editor breaks the single-process memory budget and limits Writing Tools to a panel. Record 0001 chose the stack, and docs/architecture.md keeps the reasoning.

Rules the code keeps

  • The raw Markdown text is the only model. Rendering changes attributes, never characters.
  • Opening a file never writes it and never normalizes it. Bytes you did not edit never change, the byte-order mark and line endings included.
  • Every write, from any writer, takes one path: detect the change, compare it with the last known contents, snapshot, merge three ways, apply, and save only if the disk still matches.
  • Conflicts never enter the file. The other version shows as a card until you choose.
  • Nothing restyles the text or applies an outside change while an input method is composing.
  • Nothing touches the text view's layoutManager, which would switch it to TextKit 1.
  • After five seconds without input, nothing runs: no timers, no animation, no blinking caret.

The app

The editor

The editor is an NSTextView on TextKit 2. TextKit 1 and the switch between the two are deleted, so each feature is built once (0004). Inline Writing Tools needs TextKit 2; on TextKit 1 it shows its results in a panel.

The styler sets attributes only. Syntax hides by turning its color clear, so the characters on screen are always the characters in the file.

A keystroke reparses one window: the top-level block or list item that holds the edit, plus the neighbors that can continue into it. A window that does not hold keeps its neighbors' styling until the whole document reparses off the main thread after 300 ms idle (0006).

Documents and saves

Each file is an NSDocument. AppKit's autosave in place is off, which also turns off the Versions browser. Dewline keeps its own history in snapshots instead.

  • The app autosaves 2 s after your last edit, through the engine.
  • ⌘S first lands whatever the file holds now, then saves.
  • Documents read off the main thread, since the engine reads, hashes and snapshots the file as it opens.
  • A save that the engine refuses writes nothing to your file. Your text goes to the file's draft snapshot instead.

The engine

The engine is a Cargo workspace of four crates. dewline-core holds everything that touches files. dewline-ffi adds diagrams, math and the UniFFI surface. dewline-sync holds collaboration. dewline-cli is the command.

Parser

pulldown-cmark 0.13.6 and one extension pass in core::md are the only Markdown parser. The extension pass adds the Obsidian syntax: wikilinks, embeds, tags, callouts. Every consumer reads the same blocks and tokens, so each construct is written once (0006).

The parser passes the 652 CommonMark 0.31.2 examples and the GFM table, strikethrough and task list examples. The parser and the merge each have a fuzz target in core/fuzz.

Change engine and merge

The change engine lands outside writes into an open document without losing a byte. Rust keeps each document's base (the disk bytes the buffer last absorbed), the disk as last seen, the landing that waits for its commit, and the pending changes and conflicts. Swift keeps the buffer.

The merge is three-way: the file's new version (theirs) lands on the open buffer (yours) against the base. It diffs lines first, then the words inside each changed region, both with imara-diff's Myers algorithm. Offsets are UTF-16 code units, as the Swift buffer counts them, and never fall inside a \r\n.

Compare-and-swap saves

A save writes only if the file still holds the bytes the save was based on, checked by BLAKE3 hash. Bytes that hash to the base write nothing.

The new bytes go to a hidden sibling that takes the file's mode, owner, group, flags and extended attributes, and the sibling is renamed over the file. A symlink, a file with other hard links or an access control list is written in place instead, through the descriptor that was hashed. A failed write in place puts the original bytes back.

Snapshots

Snapshots live in ~/Library/Application Support/dev.arkwerx.dewline/snapshots/, never beside your files. The store is content-addressed:

  • blobs/ holds each version once, zstd-compressed and named by the BLAKE3 hash of its bytes.
  • files/ holds one index per file, named by the hash of its path.
  • tmp/ holds writes in progress. Each write is synced, renamed into place and its folder synced, so a crash leaves the old file or the new one whole.

Files and saves says when a snapshot is taken and how long it is kept. Security and privacy covers permissions and what is never snapshotted.

Path jail

The MCP server, dewline:// links and the images an export inlines all reach files through one jail in core::jail. A path is resolved with realpath and must lie inside the root. It is then opened from the root's descriptor with no symlink allowed anywhere on the way (O_NOFOLLOW_ANY), and the opened file's own path must still lie inside the root. A link or folder swapped in between the two steps opens nothing. A property test throws mixes of names, dots, links and loops at it.

No JavaScript runs on your notes anywhere. Math and diagrams each stop at 50 KB of source and a 250 ms render, and a diagram's picture stops at 16 megapixels (16,777,216 pixels). A block that fails or runs over shows its source, with a dim line naming the error.

Export

The engine writes HTML and DOCX. The app adds PDF: it lays out the engine's HTML in a web view that runs no page script, keeps no data and follows no link, then cuts it into pages between top-level blocks. The dewline command hands a PDF export to the app through a dewline://export link, a hand-off that fails in 0.1.0 (Command line).

Across the boundary

The app reaches the engine through UniFFI 0.32.2. scripts/build-xcframework.sh builds the engine as a dynamic framework, DewlineFFI.xcframework, so the app and its Quick Look preview share one copy in Dewline.app/Contents/Frameworks. The Swift package MdCore wraps the generated bindings.

  • A parse returns flat records: block and token kinds with UTF-16 ranges, the way NSString counts.
  • Release builds unwind, so a panic in Rust returns as a Swift error, not a crash.
  • Engine calls that read or write files run off the main thread, one at a time per document. commit never waits behind them.

An outside change, disk to screen

When git, a sync app, a script or a coding agent writes the file you have open, the change takes the same eight steps every time.

Three rules hold along the way.

  • The file is snapshotted before anything lands, and your unsaved typing is snapshotted before the merge. Any step can be undone from File > Snapshots.
  • While git holds index.lock, or an agent's hooked tool call on the file is open, the landing waits, 10 s at most. A checkout or a patch lands after the writer finishes, not halfway through.
  • A change gets a writer's name only when that writer's hooks report it through dewline notify, which sends paths and BLAKE3 hashes, never content. Anything else shows as Unknown (0007).

Other front ends

Quick Look

The Quick Look preview is a sandboxed app extension. It returns the page that HTML export writes, as data, in the app's stylesheet. The page runs no script and loads nothing from the network. Diagrams and math show as their source, and no image is inlined.

The dewline command

The command ships inside the app at Dewline.app/Contents/Helpers/dewline. It links dewline-core directly, with no UniFFI, no Mermaid, no math and no collaboration stack, so it is one small binary with no framework beside it. On a release build for arm64, it links only system libraries:

$ otool -L dewline
dewline:
	/usr/lib/libiconv.2.dylib (compatibility version 7.0.0, current version 7.0.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1359.40.3)

The command reaches the running app through one Unix socket, ~/Library/Application Support/dev.arkwerx.dewline/run/control.sock. A connection carries one JSON line, such as an open request or a hook's claim. Command line and MCP server cover what it does.

Updates

Sparkle 2.10.0 updates the app. The appcast at dewline.arkwerx.com/appcast.xml is signed, and so is each update archive, with an EdDSA key whose public half is in the app's Info.plist. Sparkle checks the archive before it extracts it. The updater starts only in builds signed with the ArkWerx Developer ID, so debug and unsigned builds never contact the feed. An update downloads in the background and installs when you quit. The app never restarts on its own.

Collaboration

Live collaboration runs on the same change engine (0009).

  • Mirror. dewline-sync keeps one Loro document per shared file, with one text container. The .md on each Mac stays the source of truth. Loro carries edits between Macs and nothing reads it back from disk. The host seeds it from the file as it is when Share is first pressed, so earlier history never leaves the Mac.
  • Transport. iroh 1.3.0, peer to peer, with a relay when no direct path opens. The invite link carries the host's address, so nothing is published to an address lookup service. A direct stream carries joins, keys and removals. An iroh-gossip topic carries edits and cursors.
  • Invites. A link holds a random 256-bit capability that the host spends the first time anyone presents it. The host approves each join by name.
  • Keys. Each gossip message is sealed with XChaCha20-Poly1305 under the document key and signed with the sender's ed25519 node key. Each approval or removal makes a new document key, so a removed Mac can read nothing new.
  • The seam. A collaborator's edit reaches the engine as one replace from that collaborator. The engine snapshots your buffer first, at most every 30 s. The app holds the edit while an input method composes and applies it outside your undo history, with the caret kept in place.

Not built yet: rejoining after a dropped connection or a restart (a guest needs a new link today), and edits larger than iroh-gossip's 1 MiB message.
